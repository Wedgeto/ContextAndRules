# Обзор архитектуры: Multi-Agent Swarm Protocol (V4)

Данный документ описывает логику работы и взаимодействия агентов на основе обновленного системного промпта (**GEMINI.md**). Система спроектирована для работы в условиях жестких ограничений контекстного окна в крупных и долгоживущих проектах.

---

## 1. Топология Роя (Swarm Topology)

Система разделяет один и тот же ИИ-инструмент на две функциональные роли, которые определяются при старте сессии:

*   **MASTER_ORCHESTRATOR**: «Мозг» и дирижер проекта. Он отвечает за высокоуровневые решения, архитектуру и общую координацию.
    *   *Память*: Видит только текущую ситуацию и общие правила. Игнорирует старые логи для чистоты мышления.
*   **WORKER_ANALYST**: «Узкий специалист» (субагент). Активируется для выполнения конкретных, тяжелых задач (анализ гигантских логов, написание тестов, парсинг данных).
    *   *Память*: Полная изоляция. Знает только свою задачу и входной файл. Не имеет права менять код без разрешения.

---

## 2. Шина данных (Data Bus) и Управление памятью

Вместо одного файла состояния, система использует структуру директорий в `docs/agent/`:

| Директория/Файл | Назначение |
| :--- | :--- |
| `_core/GLOBAL_STATE.md` | "Декларация о независимости" проекта: цели, стек, архитектура. |
| `_core/HISTORY.md` | Живой лог выполненных задач текущего этапа. |
| `sprints/current.md` | Активный Todo-лист (Backlog) текущего спринта. |
| `exchange/outbox/` | Место, куда Мастер кладет "приказы" (Манифесты) для Воркеров. |
| `exchange/archive/` | Кладбище выполненных задач и ротированных логов истории. |

---

## 3. Протокол Делегирования (CaaS)

Процесс обработки сложных задач разбит на 4 этапа:

1.  **Trigger**: Мастер понимает, что лог слишком большой (>500 строк) или задача слишком "шумная".
2.  **Manifest**: Мастер создает файл `task_[ID].md`. В нем жестко задаются: Роль (напр. `QA_TESTER`), Входные файлы и Ожидаемый формат ответа.
3.  **Handoff**: Пользователь открывает новый чат, который, видя манифест, автоматически становится Воркером.
4.  **Sync**: Воркер пишет результат в `inbox/result_[ID].md`. Мастер поглощает этот результат и продолжает работу.

---

## 4. Механизмы защиты (Safety & Hygiene)

*   **Surgeon Rule**: Агент не имеет права править файл, который не «прочитал» в текущем окне чата.
*   **No Placeholders**: Запрещено использование комментариев типа `// ... остальной код`. Только полные, готовые к вставке блоки.
*   **Memory Rotation**: При достижении лимита или конце спринта, `HISTORY.md` переносится в архив, а на его месте создается чистый файл. Это предотвращает "замыливание взгляда" у ИИ.
*   **Fallback Protocol**: Если Воркер не нашел данные, Мастеру запрещено их галлюцинировать. Мастер обязан запросить уточнение или вмешательство человека.

---

## Итог
Эта архитектура превращает диалог с ИИ из "переписки в мессенджере" в полноценную **операционную среду**, где каждый байт контекста расходуется эффективно, а история проекта сохраняется в структурированном и читаемом виде.
